Agent payment authorization

Prove an agent was authorized before it spends.

Bolyra verifies delegated spend mandates before x402/MPP payments and emits signed receipts for audit, disputes, and compliance. The same verifier boundary generalizes to verified agent actions: policy enforcement, signed action receipts, and a tamper-evident audit trail in front of any MCP server or agent platform. Two independent implementations reproduce it in public, from pinned commits.

What crosses the wire

Mandate in, verdict out, receipt signed.

1 · The mandate

issueMandate({
  agent: "shopper-bot",
  audience: "api.merchant.example",
  tier: "small",   // < $100
  expires: "+1h"
})

One operator signature binds agent, payee audience, spend tier, and expiry into a tamper-evident mandate.

2 · The verdict

GET /api/report ($25)
→ 200 ALLOW

GET /api/bulk-export ($500)
→ 403 DENY, before payment
{ "code": "request_mismatch",
  "title": "Mandate Does Not
    Cover This Request" }

Verified before any payment logic runs. Over-scope and missing mandates fail closed with RFC 9457 problem details.

3 · The receipt

seq=1  allowed=true  $25
merchant=api.merchant.example
signer=0x688c…2f4e
payloadHash=0x7358…7635
// ES256K, hash-chained
// verifyReceiptChain → true

Every decision, allow and deny, emits a signed receipt on one hash chain. Verifiable offline by anyone with the public key — and instance-bound: a third party can recompute exactly which action instance a decision governed from the receipt alone.

All three are real output from npx @bolyra/mpp demo: real verification path, stub transport.

Every call, checked

Four checks on every tool call.

1

Credential Verification

verifyBundle() checks ZKP proof, delegation chain, scope commitment, expiry. 401 on failure.

2

Tool Policy

YAML config maps tool names to permission bitmasks. read_file needs READ_DATA, delete needs WRITE_DATA. 403 on insufficient.

3

Replay Protection

Session nonce checked against MemoryNonceStore or Redis. Same nonce twice = rejected.

4

Audit Receipt

ES256K-signed receipt for every decision. Allow or deny. Timestamped.

Open verifier boundary, no lock-in

The External Verifier Contract is Bolyra's open host-to-verifier boundary: a host sends one verification request and gets a fail-closed allow/deny verdict from a classical, ZK, or external verifier. Run the published conformance suite, explore the reference implementations, or verify locally with bolyra verify. Bolyra maintains the spec, conformance vectors, and reference hosts.

Revocation can be enforced at the host↔verifier boundary. In examples/managed-revocation, an allow requires a trusted signing key and an active, registered binding. After revocation, the next presentation is denied. Revocation is terminal for that binding: it cannot be re-registered. The example demonstrates register, allow, revoke, and deny, while an independent credential continues to receive an allow verdict.

To request a managed-revocation pilot, email your operator public key to hello@bolyra.ai.

Prove it yourself. @bolyra/evc-conformance@0.7.0 tests both sides of the boundary, regardless of implementation language, with no project install step and no Bolyra runtime: 30 host-behavior vectors against any HUT-compatible host process, and 11 domain-agnostic wire-envelope vectors against any spawnable verifier (no assumptions about proof-bundle semantics). The contract is specified in draft-kondoju-evc on the IETF datatracker (revision -02, September 2026), and a first independent external implementation (khandrew1/mcp-use-evc-example) was built from the spec text alone and passed 27/27 host-behavior vectors from vector set 0.5.0 at commit 17642a5 — listed with permission in IMPLEMENTER.md §9. A second independent external implementation (stillmarcus24/x402-authority-verifier-kit) is a verifier built from the spec text against the x402 authorization-evidence profile. We reproduced its 39/39 result against its own pinned corpus in a network-isolated run at commit 35e209d, and it has since passed the Bolyra suite on the verifier side: 11/11 wire-envelope vectors at commit 1aa9d88, plus the §7.1 config-fault vector, which asserts that a corrupt trust configuration yields deny code=internal_error with a non-zero exit and never fails open. That is wire-envelope and exit-contract coverage, not full EVC conformance. It is also listed in §9 with the author's explicit permission. Every published claim, with its pins, is on the conformance page:

npx @bolyra/evc-conformance --host "/path/to/your-host --flags"
npx @bolyra/evc-conformance --verifier "/path/to/your-verifier --flags"

Exit 1 on failure, --json emits the vector-set SHA-256 for CI. Full pass path: spec/IMPLEMENTER.md.

Packages

Integrations and tools

Plug Bolyra into your agent framework, wallet, or payment flow.

Spend authorization

@bolyra/mpp@0.6.0: operator-signed spend mandates verified before MPP payments execute; every gate decision receipt carries the signed instance block whenever the spend facts are resolved. A mandate authorizes a spend tier for each request, with no cumulative spending budget. In 0.6.0, coversAmountUsd selects that tier, and issuance reports the authorized range. @bolyra/payment-protocols@0.8.0: x402 authorization and Stripe ACP spend gating against delegated scope, plus the x402 EVC authorization-evidence profile: the x402 retry carries authorization evidence alongside the payment credential; the resource server checks it fail-closed before payment logic proceeds. Try: npx @bolyra/mpp demo.

Verifier and gateway

@bolyra/gateway@0.6.0 npm v0.6.0: reverse proxy in front of any MCP server, per-tool policy, replay protection, signed receipts, Docker or npx. @bolyra/cli@0.9.0: bolyra verify, a spawnable external verifier any host can call. @bolyra/evc-conformance@0.7.0: npx @bolyra/evc-conformance --host "<cmd>" for hosts, --verifier "<cmd>" for verifiers — 42 wire-contract vectors, zero runtime dependencies.

Receipts and audit

@bolyra/receipts@0.11.0: ES256K-signed auth and commerce receipts, hash-chained, offline-verifiable, signer discovery via /.well-known/bolyra-signers.json. New: receipt instance binding — a domain-separated, third-party-recomputable reference (birv1:) binds each decision to the specific action instance it governed, so a relying party derives it from the action’s own facts with no callback to the issuer. The spec was design-reviewed in public with the author of argentum’s action_ref, and verifyInstanceBinding() is public API: signature validity and instance validity are different claims, and bolyra receipt verify checks both. Replay Check GitHub Action: replays receipt history against policy on every PR.

MCP and tool enforcement

@bolyra/mcp@0.6.5: middleware with dev mode, per-tool gating, stdio and HTTP. @bolyra/shield@0.2.0: stdio auth proxy with learn mode that writes a default-deny shield.yaml from the server's tool list. Both on the official MCP Registry.

Frameworks and ZK

TS SDK at v0.6.1 and Python SDK v0.5.0. Adapters for Vercel AI SDK, OpenAI Agents, LangChain, and CrewAI. @bolyra/circuits: prebuilt Groth16 artifacts, no Circom compiler needed. ZK upgrades use the same verifier boundary when privacy-preserving delegation is needed.

Differentiation

Why not just OAuth?

Capability OAuth / JWT Bolyra
Delegated scope narrowing Manual policy engine Circuit-enforced, one-way
Per-tool permissions Custom middleware per tool YAML config, one gateway
Replay protection Token expiry only Nonce store (memory / Redis)
Signed audit trail Application logging ES256K receipts on every call
Privacy-preserving upgrade N/A ZKP path: verifier never sees identity

Standards

Specified in the open

Not just code: a written contract, a DID method, and a conformance suite anyone can run.

IETF

Internet-Draft, revision 02 (not a standard)

draft-kondoju-evc-02

The External Verifier Contract: how a host asks a verifier for a verdict on an agent's proof bundle, and what a verdict and receipt must contain. Registry closure, fail-closed precedence, implementation status. On the datatracker; the document can still change.

Identifiers

DID method

did:bolyra

W3C Decentralized Identifier method for Bolyra identities. Supports both human and agent DID documents with ZKP-aware verification methods.

Conformance

Test vectors

spec/test-vectors.json covers handshake, delegation chains, enrollment, proof envelopes, session tokens, receipts, host behavior and the verifier envelope; CI runs the suite on every change; experimental classes are skipped by the runner and say so. 42 of them, 30 host-behavior, 11 domain-agnostic wire-envelope, and the §7.1 config-fault, ship as @bolyra/evc-conformance@0.7.0 to test any implementation, in any language, with no Bolyra runtime.
