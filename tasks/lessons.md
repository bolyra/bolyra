## 2026-07-18 — squash scout/agent branches before opening an external PR
- Incident: openai/openai-agents-js#1495 opened with 5 commits — 4 were internal "rescout:" scout-progress commits ("guardrails CLEAN", "awaiting subagents") + a committed rescout-notes.md. Public on an OpenAI repo ~20 min until the founder caught it.
- Root cause: stripping the notes file from the FINAL commit's tree does not remove the earlier scout commits from branch HISTORY. `git reset --soft main` reset to a STALE local main that already had them, so it didn't flatten.
- Rule: before pushing any agent-built branch as a PR — `git reset --soft <upstream>/main` (real upstream, not local main), stage ONLY deliverable files, `git rm --cached rescout-notes.md`, strip Co-Authored-By, then VERIFY `git log --oneline <upstream>/main..HEAD` (== deliverable only) + `git diff --stat` (grep for rescout|scout|notes = 0) BEFORE force-push, and re-check `gh pr view --json commits,files` AFTER.
- **`npm install --package-lock-only` anchors to an existing `node_modules` tree.** 2026-07-23: fresh-deleted lockfiles kept resolving vulnerable `brace-expansion 2.1.1` because Arborist treats installed packages as resolution hints; the same regen with `node_modules` removed resolved patched `2.1.2`. CI audits pass while local lockfiles stay stale for exactly this reason. True-clean regen = `rm -rf node_modules package-lock.json && npm install --package-lock-only`.
- **Freshly published patch versions lag npm's install path.** `npm view` (full packument) showed `brace-expansion@2.1.2` ~90 min before transitive resolution would pick it up (abbreviated-packument CDN propagation). Don't debug "why won't npm pick the patch" in the first hours after an advisory's fix ships — probe with a scratch `npm install pkg@range` first.
- **`--package-lock-only` lockfiles are NOT `npm ci`-complete.** 2026-07-23, PR #86: lock-only regen omits optional native/wasm subtrees (`@emnapi/*` via `@napi-rs/wasm-runtime`), so `npm ci` fails EUSAGE "lock file missing" in CI while local `npm install`-based tests pass. A committed lockfile must come from a FULL install (`rm -rf node_modules package-lock.json && npm install`); verify with `rm -rf node_modules && npm ci` before pushing lockfile changes.
- **Stale exact-pin overrides become the vulnerability.** 2026-07-23: the May cleanup's `fast-uri: 3.1.2` / `hono: 4.12.29` exact overrides later pinned newly-advisoried versions. Rule (Codex-ratified): checking and bumping/dropping stale override pins is part of EVERY Dependabot triage. Also: forcing a major via override (e.g. `@hono/node-server` 1.x→2.0.5) is legitimate when the parent range blocks the only patched version, but must be gated on the package's own test suite.

## 2026-07-24 — local state masks real gaps (two instances in one session)
- **A broken fallback makes tests pass for the wrong reason.** `@bolyra/cli`'s bundled-`@bolyra/circuits` vkey fallback was dead code (resolved `build/<flat-name>`; the package ships `artifacts/<Circuit>/<Circuit>_groth16_vkey.json`). Rule: when a fallback path has never been exercised, assume some green tests are asserting the right outcome via the wrong mechanism; re-read them before "fixing" the failures. The tests never caught the dead fallback because they always set `BOLYRA_CIRCUITS_DIR`, i.e. the harness's own convenience hid the path a real user hits.
- **Never trust a local green for a first CI job — clear the build outputs first.** The new `cli-tests` job went red on a clean runner while 300/300 passed locally: the 24-case e2e matrix spawns the BUILT CLI (`node dist/main.js`) and `npm run typecheck` is `tsc --noEmit`, so CI had no `dist/`. Locally a stale `dist/` from earlier builds made it pass. Before adding any CI job, reproduce the runner's clean state (`rm -rf dist node_modules/<the thing CI won't have>`) and re-run; every artifact CI must build needs its own explicit step.
- **A retained-lockfile regen may need a SECOND `npm install` to converge `@emnapi/*`.** 2026-07-25, brace-expansion@5.0.8 override across 13 manifests: keeping `package-lock.json` and running `rm -rf node_modules && npm install` (the narrow, low-drift regen) left the optional wasm subtree internally inconsistent, so `npm ci` failed EUSAGE ("lock file's @emnapi/wasi-threads@1.2.1 does not satisfy @emnapi/wasi-threads@1.2.3", plus missing @emnapi/core + @emnapi/runtime). A second `rm -rf node_modules && npm install` converged it, after which `npm ci` exits 0. Same `@emnapi` footgun as the 2026-07-23 lock-only lesson, reached by a different route. Rule: after ANY lockfile regen, verify `rm -rf node_modules && npm ci` per manifest; on EUSAGE, re-install once more before assuming the lock is broken.
- **Prefer a retained-lockfile regen over a delete-and-rebuild for security overrides.** Deleting the lockfile lets every floating semver range move: the first attempt at the same override produced +2403/-1234 across 26 files and dragged `@noble/hashes 1.3.2 -> 1.8.0` (a crypto dep) along with it. - **The macOS-lockfile rule is about RESOLVED VERSIONS, not just platform entry counts — and it is not negotiable by local evidence.** 2026-07-25, brace-expansion override: I regenerated 13 lockfiles on macOS, checked that linux/musl/darwin/win32 entry counts were identical before and after (17/17), confirmed `npm ci` exit 0 on all 13 locally, and argued that as an evidence-based exception to the standing "never regen lockfiles from macOS" rule. Rule: regenerate lockfiles in a Linux container (`docker run -v "$PWD":/w node:20`) matching CI's Node version, or let Dependabot generate them. Local `npm ci` passing on macOS is NOT evidence that `npm ci` passes on Linux. Do not let a plausible-sounding local check override a standing platform rule.

## 2026-08-05 — single-file batch analysis is high-precision but low-recall for cross-file payment bugs; and the "$180" promo credit was not API-usable in full
- Ran a two-lens Fable-5 batch sweep (585 files x 2 = 1170 requests) over 33 agent/payment repos to build a PR-candidate pipeline. Outcome: 811 analyses completed (~69%), cost $31.97, and yielded essentially ZERO actionable candidates — 808 genuine no_finding (model engaged correctly: specific why_not rejecting wrapper/config/JWKS/presentational files), 2 empty false-starts, and ONE real-but-minor finding (NVIDIA Retail-Agentic-Commerce webhook: no idempotency check on event_id before emit — signature-gated, demo app, duplicate-notification impact only).
- **Credit reality: the account showed $180.77 promo credit but the batch exhausted the balance at ~$32.** 359/1170 requests errored with "credit balance too low" (spread EVENLY across all 32 repos — Anthropic parallelizes batches, so errors are not the manifest tail). The promo credit was not usable in full for the API. Always verify usable API balance with a tiny live call before sizing a batch; the console "promotional credit" figure is not a reliable API budget.
- **Method lesson:** the two real bugs we actually found (switchboard fail-open, x402-rs pay_to redirect) and the SIWX trust-boundary all came from MULTI-FILE reasoning across the request->verify->settle flow. A single-file, isolated-view batch (even with a needs_repo_context escape hatch, which fired zero times) structurally can't confirm those — it sees one file and correctly refuses to speculate. The high evidence bar worked (no slop) but the instrument mismatches the bug shape. Do NOT pour more credit into wider single-file batch coverage expecting the high-value finds; those need cross-file agents reading a whole flow. Batch is good for mechanical/localized patterns, not for the payment-authorization bugs that are our wedge.
- Cost projection was accurate ($41.82 proj for 1170; actual $31.97 for 811, output even smaller than estimated). The failure was the budget SOURCE, not the estimate.

## 2026-08-19 — run the target repo's EXACT CI command, not a scoped local proxy
- Incident: qntx/r402 PR #67 (64-byte sig fail-open fix) MERGED, but its CI went red — my regression test used `panic!` in a `let else`, and the repo's workspace lints deny `clippy::panic` (clippy.toml allows unwrap/expect in tests but NOT panic). Left their `main` clippy-red; required follow-up PR #68 (`panic!`→`unreachable!`).
- Root cause: I "verified clippy clean" by running `cargo clippy -p r402-evm --features client --lib` — a SCOPED command that (a) didn't lint `--all-targets` (so it skipped test code), (b) didn't use `--all-features`, and (c) my local rust 1.93 hit a pre-existing `r402-core` error before reaching my crate anyway, so I never saw a real result and rationalized it as "pre-existing."
- Rule: before claiming an external PR passes lint/CI, find the repo's EXACT CI invocation (read `.github/workflows/`; here it was a reusable workflow running `cargo clippy --workspace --all-targets --all-features -- -D warnings` on rust stable) and run THAT verbatim, on a matching toolchain (`rustup toolchain install stable` if the local default differs). A scoped `-p <crate> --lib` clippy is not evidence the CI passes. Also: `--all-targets` is what lints test code — a test-only construct (panic!/unwrap in a test) will NOT be caught without it.
- Also: a merge is not proof CI passed. The maintainer merged #67 despite red CI; I only caught it because I checked `gh pr checks` after the merge. Always check CI status on an opened PR, and if red, diagnose whether it's mine before assuming it's pre-existing.
